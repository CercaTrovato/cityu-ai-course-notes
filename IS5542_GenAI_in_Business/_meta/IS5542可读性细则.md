# IS5542 可读性细则

本文件只补充 IS5542 的学科要求。句子、段落、版面、表格尺寸、分层和三种阅读场景，全部按 [[可读性总规则]] 执行。两者冲突时以总规则为准；原件或正式题面需保留特殊格式时，旁边另给可读解释。

本课读者懂 AI 的基本概念，但不熟悉企业怎样落地。最常卡住的是四件事：

- 一个业务案例里，AI 到底做了哪一步、人做了哪一步；
- 厂商自己报的数字和第三方测的数字混在一起；
- 基准测试（benchmark）的分数在测什么、越高是否越好；
- agent 系统由很多组件组成，一个请求经过它们的顺序说不清。

## 1. 本课默认版式（补充总规则 §3）

| 内容类型 | 默认版式 |
|---|---|
| 一个企业 / 行业案例 | 案例卡：两列表，固定字段（见 §2） |
| 案例里的效果数字 | 数字 + 来源类型 + 日期（见 §3） |
| 基准测试分数 | 先给基准说明表，再给分数表（见 §4） |
| 提示词示例 | ```text 代码块 + 逐部分说明表（见 §5） |
| agent / harness / RAG 的工作过程 | Mermaid 数据流图 + 追踪一个具体请求的编号步骤（见 §6） |
| 讲义的分段结构概览 | 列表，一段一项：名称（页码）+ 一句话（见 §7） |
| 设计题、自测题的作答 | 编号列表，一个设计决策一项；并列小点用二级列表（见 §7） |

## 2. 业务案例卡

### 2.1 规则

每个案例先放案例卡，再写分析。字段固定如下，单元格每格 ≤ 40 单元、最多 2 句：

| 字段 | 写什么 |
|---|---|
| 公司与时间 | 公司名、年份 |
| 业务问题 | 不用 AI 时卡在哪里 |
| AI 做什么 | 输入 → 处理 → 输出，各一个短语 |
| 人做什么 | 审核、兜底、例外处理 |
| 效果 | 数字，按 §3 标来源 |
| 风险或失败 | 出过什么问题，或讲义提到的限制 |
| 本讲用来说明 | 对应概念，回链小节 |

### 2.2 示例

❌ 不合格（示意写法：案例叙述、效果数字和教训写成一段）：

> Klarna 用 AI 客服处理了大部分对话，相当于几百个人工客服，客户满意度也差不多，但后来发现情绪化投诉处理不好，又重新招人，说明不确定任务还是要人兜底。

✅ 合格：

> | 字段 | 内容 |
> |---|---|
> | 公司与时间 | Klarna，讲义 p.57（NotebookLM 信息图） |
> | 业务问题 | 客服对话量大 |
> | AI 做什么 | 客户聊天 → AI 直接回复 |
> | 人做什么 | 复杂、情绪化的问题升级给人 |
> | 效果 | 230 万次对话，约占全部聊天的 2/3〔讲义未注明来源〕 |
> | 风险或失败 | 对情绪问题回答机械，满意度受损，于是转回“升级给人”的模式 |
> | 本讲用来说明 | 只看效率指标不够；高情绪任务要有人兜底（M03 §2.9.4） |

数字一律按讲义原文填。讲义没有给出的数字，不能凭印象补。

## 3. 效果数字的标注

1. 每个效果数字后面用括号标来源类型：〔厂商自报〕〔第三方评测〕〔学术论文〕〔讲义未注明来源〕。
2. 同时写时间：“2025 年发布”“截至讲义日期”。
3. 一句只放一个效果数字。两个数字比较时，写清分母相同吗、时间相同吗。
4. 营销形容词（革命性、颠覆、前所未有）只能出现在引用块的原文里。笔记自己的话不用。

---

## 4. 基准测试

### 4.1 规则

1. 先放基准说明表：基准 / 测什么 / 分数范围 / 越高越好吗。一个基准一行，单元格 ≤ 25 单元。
2. 再放分数表：行是模型，最多 8 行；列是基准，最多 5 列。表头写日期：“分数（截至 2026-09）”。
3. 表后“读第一行”，再写两条限制：分数之间能不能直接比较（不同评测设置），以及这个分数和本课项目任务有多大关系。

### 4.2 同类示例：人物与观点表

基准表和人物表犯的是同一种错：把说明塞进单元格。

❌ 不合格（M02 §2.2 引子的表格：一个单元格同时写人物经历、观点原话和页码，长 82–94 单元）。

✅ 合格：人物经历做一张“人物 / 机构 / 本讲引用的观点”三列短表，原话放表后引用块。

## 5. 提示词示例

1. 提示词全文放 ```text 代码块，保持原样。
2. 代码块后放逐部分说明表：部分 / 原文开头几个词 / 作用。
3. 对比两个提示词时，只标出差异部分，不重复全文。

## 6. agent 与系统流程

### 6.1 规则

1. 先用 Mermaid 画数据流，节点名和正文里的组件名一致。
2. 再追踪一个具体请求，编号步骤，每步一行：哪个组件 → 收到什么 → 做什么 → 交出什么。
3. 组件定义第一次出现：中文（English）+ ≤ 20 单元的人话。一段最多引入 2 个组件。
4. “要平衡的两端”一类的对照，用两行对比表，不写成一句里的“A vs B”。

### 6.2 示例

❌ 不合格（M03 §2.7.7，一段 259 单元：系统提示的定义、四个组装来源、两端权衡和建议原话全在一段）：

> 右栏讲另一件事——**系统提示组装**（system-prompt assembly）。"系统提示"是每次请求最前面那段告诉模型"你是谁、该怎么做"的文字……而是运行时从四样东西组装出来的：基础人设（base persona）、发现的项目 / 组织指令……要平衡的两端：**过度规定**……vs **规定不足**……

✅ 合格：

> 系统提示是每次请求最前面那段文字，告诉模型“你是谁、该怎么做”。在生产系统里，它不是写死的，而是每次运行时拼出来的（讲义 p.31）。
>
> 拼的材料有四样：
>
> 1. 基础人设（base persona）。
> 2. 项目或组织的指令，比如一份 `CLAUDE.md`、一份内部文风指南。
> 3. 当前可用的工具目录。
> 4. 当前环境状态。
>
> 写系统提示要在两端之间找平衡：
>
> | 写过头 | 写不够 |
> |---|---|
> | 规则写成僵硬的 if-else | 指导含糊 |
> | 遇到没预料的情况就崩 | 假设模型知道它其实不知道的背景 |
>
> 讲义的建议见下方引用。
>
> > "start minimal, add specificity only in response to observed failure modes."
>
> 意思是：先写最少的规定，只在观察到具体失败后再补。

## 7. 概览与设计题

1. §0 速览里讲义的分段结构用列表，一段一项：“名称（p.8–18）：一句话”。
2. 设计题答案按设计决策分项，一项一个决策，并列小点用二级列表，不写 ①②③。

❌ 不合格（M03 §0，一段 329 单元，六段讲义结构和每段要点用破折号串成一句）：

> 讲义按页脚自标的六段走：**1 基础与 agency**（p.8–18）——agent 这个概念有 80 年历史……；**2 agent 系统**（p.19–40）——核心概念 **harness**……；**3 架构**（p.41–51）——……

✅ 合格：

> 讲义分六段：
>
> 1. 基础与 agency（p.8–18）：什么才算 agent，四个支柱和四级自主性。
> 2. agent 系统（p.19–40）：核心概念是 harness，即模型外面那层运行时。
> 3. 架构（p.41–51）：三种成型架构，各适合什么任务。

## 本课高风险术语（提示清单）

每个独立学习单元首次实际用到这些概念时，至少给 1 句具体解释；跨单元可用 1 句唤醒加回链。下表是说明方向，不是逐字替换词典。R6d 只报待核提示，不能认证解释正确。

| 术语 | 需要讲清的意思 |
|---|---|
| 幻觉 | 模型生成了看似可信但没有根据的内容 |
| 检索增强 / RAG | 先找相关材料，再让模型据材料回答 |
| 基准测试 / benchmark | 用约定题目和评分方式比较系统表现 |
| 人工接管 | 达到约定条件时，由人继续处理请求 |
| harness | 组织模型、工具、状态和执行规则的运行程序 |

❌ 不合格：把表中若干术语并排写成结论，让读者自己补步骤。

✅ 合格：选本题的一个对象，逐步写它发生了什么变化，再用术语命名，并说明结论来自哪一步。
