# 外卖客服场景：数据与模拟可行性分析

本页回答两个问题：有没有现成的外卖数据集？如果数据要自己模拟，项目还站不站得住？

结论先说：没有现成的外卖客服对话数据集，但有美团公开的真实订单时间数据。用真实订单时间加上团队自写的规则，在 τ-bench 的框架里搭一个外卖客服考场，是可行的。只是工作量和“自己出题自己考”的质疑都比直接用 τ-bench 零售大。

## 1. 现有公开数据盘点（2026-10-31 检索）

| 数据 | 内容 | 能用在哪 | 限制 |
|---|---|---|---|
| [美团 INFORMS TSL 研究挑战数据](https://github.com/meituan/Meituan-INFORMS-TSL-Research-Challenge) | 真实外卖订单：数据论文记 56.8 万订单、4955 名骑手、4962 家商户，单一城市 8 天（2022-10）。每单都有承诺送达时间（`estimate_arrived_time`）和实际送达时间（`arrive_time`），以及下单、出餐、取餐时刻；坐标已偏移 | 算出真实的超时分布：超时多少分钟、多常见、什么时段容易超时，用来生成逼真的模拟订单 | CC BY-NC 4.0，只限非商业用途；未经许可不得向第三方分发，所以原始数据只能留在本地，不能推到公开仓库；发表须注明 “This research was supported by data provided by Meituan.”；没有投诉、退款或对话字段 |
| [Kaggle Zomato 配送数据](https://www.kaggle.com/datasets/saurabhbadole/zomato-delivery-operations-analytics-dataset) | 印度 Zomato 配送记录，有下单、取餐时间和配送用时；一篇分析文章称约 4.2 万条 | 作为第二个地区的参照 | 许可证和字段本次未能读取，待核；没有承诺送达时间，算不出“超时” |
| [Bitext 客服数据](https://huggingface.co/datasets/bitext/Bitext-customer-support-llm-chatbot-training-dataset) | 单轮问答，按意图标注：取消订单、查退款、配送时间、投诉等 | 参考客户的说法有多少种 | 电商，不是外卖；单轮，不是多轮对话；没有“正确操作”的标准答案 |
| Hugging Face 上的小型外卖或投诉数据（如 [Food-Delivery-Dataset](https://huggingface.co/datasets/shinona0011/Food-Delivery-Dataset)、[customer-complaints](https://huggingface.co/datasets/hblim/customer-complaints)） | 多为 AI 生成的评论或投诉短句 | 参考投诉措辞 | 本身就是合成数据，不比我们自己模拟更可信 |
| 美团、京东外卖、淘宝闪购的公开规则页（同学 docx 已列出） | 准时宝、超时免单等官方说明 | 写我们的模拟政策；出“规则提问实验”的题目 | 只是面向用户的说明，不是平台内部审批规则 |

一句话：真实的订单时间数据有，真实的客服对话和处理结果没有。后者无论选哪种做法都要模拟。

## 2. 模拟方案：用 τ-bench 的框架搭一个外卖考场

τ-bench 允许新增自定义领域。它的“假客户”用户模拟器和“对比数据库最终状态”的自动打分可以直接复用，我们只需要换上外卖的四样东西：

| 组成 | 外卖版怎么来 | 真实还是模拟 |
|---|---|---|
| 数据库 | 订单的承诺和实际送达时间，按美团真实分布抽样生成；商户、菜品、金额和用户为虚构 | 时间分布来自真实数据，订单本身是模拟的 |
| 政策 | 团队参考公开规则自写，例如“超时 30 分钟以上可申请补偿；有价补偿须人工批准；漏餐需上传照片”，明确标注不是任何平台的真实条款 | 模拟（有公开规则作依据） |
| 工具 | 查订单、查配送轨迹摘要、建补偿申请、提交人工审批、转人工、发通知 | 模拟系统 |
| 任务剧本 | 测试组写 50–60 个情境，每个配好正确结果，例如“超时 42 分钟、已核身份，应建 10 元券申请并进入审批” | 模拟，但正确结果由规则唯一确定，可以自动判分 |

正确结果由“订单事实 + 政策”算出，不靠人主观判断，所以仍然是客观评测。

## 3. 可行性逐项判断

| 维度 | 判断 | 说明 |
|---|---|---|
| 数据 | 可行 | 订单时间有真实依据；其余部分必须如实标为模拟 |
| 自动评测 | 可行 | 复用 τ-bench 的打分机制；不用每次人工看对话 |
| 真实平台对比 | 部分可行 | 不能大量制造真实超时。可以拿公开规则出 20–30 道题，去问平台的 AI 客服，与我们的 agent 比答案准确率和是否编造。只是提问，不下单、不投诉；记录提问日期并截图 |
| 体现 GenAI 必要性 | 有风险 | 如果剧本只是“查时间、套规则”，用 if-else 就能做。剧本必须包含需要理解语言的情况：一句话里同时说超时和漏餐；客户说法和订单记录矛盾；情绪激烈要求真人；信息不全需要追问 |
| “自己出题自己考” | 有风险 | 规则、剧本和 agent 都由我们写，容易被质疑。对策：测试组写剧本和标准答案，技术组调 agent 时不看测试集；测试集在调参前冻结；再用 τ-bench 零售跑一次作外部参照 |
| 工作量 | 偏大但可控 | 估计技术组 2 人约 4–5 天搭领域（数据结构、工具、政策、接入框架）；测试组同时写剧本约 3 天。11/2 前开工，11/15 前出评测结果，时间可行但余量小 |
| 数据合规 | 需注意 | 美团原始数据只放本地并加入 `.gitignore`；仓库只放我们生成的模拟订单和生成脚本，生成参数来自美团数据，在 slides 和报告中注明来源 |

## 4. 与“直接用 τ-bench 零售”的比较

| | 外卖模拟考场 | τ-bench 零售 |
|---|---|---|
| 场景贴近生活 | 高，同学调研和真实平台对比都能接上 | 中，普通网店售后 |
| 数据可信度 | 订单时间真实，其余模拟 | 全部虚构，但是业界公认的基准 |
| 评测客观性 | 客观，但题目是自出的 | 客观，题目由第三方出 |
| 技术工作量 | 多出“搭领域 + 写剧本”约一周 | 环境已装好，可以直接跑 |
| 讲故事 | 强：真实超时分布 + 真实平台对比 + 人工审批 | 中：需要额外说明“为什么是这家假网店” |

## 5. 可选的组合做法

主评测用外卖模拟考场，把团队调研、真实平台对比和人工审批都放进同一个故事里；同时在 τ-bench 零售上用同一套 agent 设计跑一次较小规模的测试，作为“换一个第三方出题的考场也有效”的外部证据。若时间不够，零售部分可以砍掉，只在 slides 里说明局限。

## 6. 需要团队决定

1. 主场景用外卖模拟考场，还是 τ-bench 零售。
2. 若选外卖：谁写剧本和标准答案（建议测试组），以及测试集何时冻结。
3. 是否做真实平台规则提问实验，由谁去问、问哪几家平台。
