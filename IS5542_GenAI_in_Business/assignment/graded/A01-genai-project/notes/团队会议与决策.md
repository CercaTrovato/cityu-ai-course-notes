## 2. 10/26 项目启动会（6 人出席）

会议内容如下，按原件摘录，未作修改：

- 方向：团队投票选定“客服改造”，聚焦电商客服；“投诉分流”也获多数支持。排除“销售数据自然语言分析”，理由是企业内部已有大量同类 agent，且缺少公开数据做对比。
- Agent 边界：订单查询、政策解答、商品参数等高频问题由 agent 处理；退款、赔偿等涉及资金的操作转人工审批或转人工。
- 核心指标：缩短响应时间、提高首次解决率、降低转人工率。
- 竞品调研：淘宝、京东、拼多多、抖音的问答机制、对话链路和痛点。
- 交付：15 分钟录像，包括 PPT 讲解和 Agent Demo 实操；会上表示“数据不纠结真实性，允许全模拟构建 Demo”。
- 算力：一位技术成员提出使用公司实习资源。
- 分工：分为业务调研、技术开发、测试验证三组，按角色分配如下：

| 角色 | 人数 | 会后任务 |
|---|---|---|
| 业务调研 | 1 | 调研四个平台的智能客服，收集对话记录与截图，整理调研文档；在群内确认具体场景（电商或外卖） |
| 技术开发 | 2 | 搭建 agent 工程骨架、完成核心代码与 baseline；其中一人负责算力 |
| 测试验证 | 2 | agent 雏形完成后找外部人员做真实场景测试、收集反馈；其中一人兼协调 |
| 调研／测试 | 1 | 与协调成员分担调研和测试，具体待群内确认 |

## 3. 10/27 研究方向文档（外卖方案）要点

- 结论：推荐外卖配送售后，场景为“订单已送达但超时，客户申请补偿”。电商列为可行备选，网约车不建议。文档自注其 5 分制评分是课程开发资源下的主观可行性评分，不是行业统计。
- 可借用的设计：
  - Agent 三档权限：自动执行（低风险查询与解释）、仅可建议（补偿草稿、待审批单）、必须人工决定（批准补偿、政策例外、身份冲突）；
  - 强制转人工触发条件：客户要求人工、身份校验失败、数据矛盾、没有适用政策、争议升级、涉及安全／欺诈／支付；
  - 测试案例格式：情况、期望动作、是否转人工；
  - 研究诚信提醒：不把自拟规则写成平台真实条款；不从“有售后入口”推断“后台由 LLM 决策”；不提交虚假售后请求。
- 局限：文中全部订单和规则为模拟数据，只有 8 条测试案例。“≥ 7/8”这样的目标样本太小，不足以说明可靠性，见 [[IS5542_GenAI_in_Business/notes/M02-模型全景-基准评测与提示设计|M02]] 中 pass^k 的讨论。
